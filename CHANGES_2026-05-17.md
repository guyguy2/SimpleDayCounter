# Wave 5 - 2026-05-17

## Summary

Picked **P0-2 (Room schema export)** as the wave-5 task. Lower risk than P0-3 (DAO Flow conversion) and a prerequisite for proper migrations.

## Changes

1. **`app/src/main/java/com/happypuppy/daycounter/data/database/Database.kt`**
   - Flipped `@Database(... exportSchema = false)` to `exportSchema = true`.
   - The `room { schemaDirectory("$projectDir/schemas") }` configuration in `app/build.gradle.kts` was already in place from a prior wave, so flipping the annotation was sufficient.

2. **`app/schemas/com.guy.myapplication2.AppDatabase/`** (deleted)
   - Stale schema directory belonging to a previous package ID (`com.guy.myapplication2`). Contained only a version-1 schema that did not match the current entity definition (was missing `category`, `created_at`, `target_date`, `emoji` columns and used the wrong identity hash).

3. **`app/schemas/com.happypuppy.daycounter.data.database.AppDatabase/4.json`** (generated)
   - Auto-generated by the Room compiler during `./gradlew assembleDebug` (visible as the `:app:copyRoomSchemas` Gradle task). Captures the current production schema (`id`, `name`, `category`, `created_at`, `target_date`, `emoji`) with identity hash `6e5ffba0389ef1a9d70360a831ade722`. This is the baseline future migration work will branch from.

## Intentionally NOT changed

- **`di/AppModule.kt:22` `.fallbackToDestructiveMigration()`** is still in place. Removing it without a real `Migration(1, 4)` / `Migration(2, 4)` / `Migration(3, 4)` path would crash any device that already has the old DB. The version-1, -2, and -3 schemas are gone (we never had them). Writing migrations now would be guesswork. The safe forward path is to write migrations starting from version 4 onwards (any *future* schema change must ship a real migration). The destructive fallback only fires on a downgrade or an undeclared upgrade — both of which are now blocked for v4 -> v5+ as long as future PRs add proper `Migration` objects.
- **No placeholder `MIGRATION_4_5`** was added. The roadmap doesn't yet have a forward column change committed, and adding a no-op `Migration` object would just be dead code (YAGNI). It can be added the moment a schema change is actually proposed.
- **No migration test** was added. A `MigrationTestHelper` test requires `androidTest` (instrumented) infrastructure, a real `AppDatabase_Impl`, and at least two schema versions to be meaningful. With only one schema captured (v4) there is nothing to migrate yet — the test would assert an identity. Adding the helper class itself is wave-6 work.
